# 프로젝트 기획서 — dailyfunding-fe

- 문서 버전: v2.0 · 작성일: 2026-10-01
- 상위 문서: `../../docs/PRD.md` · `../../docs/feature-spec.md` · `../../docs/tech-stack.md` · `../../docs/feature-map.md`
- 저장소 범위: 웹(Next.js) + 앱(Expo 네이티브 셸 + WebView) + 디자인 시스템 + API 클라이언트

---

## 1. 목표

데일리펀딩 클론의 사용자 접점 전체를 구현한다.

1. 투자 생명주기의 **모든 화면**을 실제 API와 연결해 end-to-end로 동작하게 한다
2. WebView와 네이티브를 **역할로 분리**해, 네이티브가 강한 영역(인증·내비게이션·알림·잠금)은 네이티브로, 콘텐츠·폼 영역은 웹으로 만든다
3. **디자인 시스템을 단일 소스**로 만들어 웹·웹뷰·네이티브 chrome이 같은 토큰을 쓰게 한다
4. OpenAPI 스키마 기반 **타입 계약 파이프라인**으로 FE-BE 불일치를 CI에서 차단한다

---

## 2. 아키텍처

```
dailyfunding-fe (bun workspace + turborepo)
├─ apps/
│  ├─ web/                    # Next.js 15 App Router — 단일 배포 단위
│  │   ├─ app/(public)/       # 홈·상품·콘텐츠 — SSR
│  │   ├─ app/(auth)/         # 로그인·가입·인증
│  │   ├─ app/(mypage)/       # 마이페이지 — 인증 필요
│  │   └─ app/(admin)/        # 운영자 콘솔
│  └─ mobile/                 # Expo RN
│      ├─ screens/            # 네이티브 화면: 잠금·간편비밀번호·알림 설정
│      ├─ tabs/               # 네이티브 탭(홈·투자·마이)
│      ├─ webview/            # WebView 스크린 + 로딩/에러 상태
│      └─ bridge/             # 브릿지 핸들러(생체인증·푸시·공유·세션)
└─ packages/
   ├─ design-system/          # 커스텀 토큰(scale/semantic) + tokens.css + React 컴포넌트
   ├─ bridge/                 # 메시지 타입·프로토콜 정의(웹↔네이티브 공유)
   └─ api-client/             # openapi-typescript 타입 + fetch 래퍼
```

### 상태 경계

- **서버 상태**(상품·원장·내역·스케줄): TanStack Query — 캐시·재검증·낙관적 업데이트
- **클라이언트 상태**(세션 표시·장바구니 건수·UI): zustand
- **폼**: react-hook-form + zod, 서버 에러 코드를 필드 에러로 매핑

### 계약 파이프라인

```
BE drf-spectacular → schema.json (CI artifact)
→ api-client: openapi-typescript 타입 생성
→ CI: 생성 결과와 커밋된 타입 diff 비교, 불일치 시 실패
```

## 4. 앱 설계 — 네이티브/WebView 역할 분리

설계 원칙: **"네이티브가 강한 것과 웹이 강한 것을 나눈다."** 화면 단위로 어느 런타임이 담당하는지를 먼저 정하고, 경계 계약(브릿지)을 타입으로 고정한다.

### 4.1 역할 분리표

| 영역                                      | 담당                        | 이유                                                      |
| ----------------------------------------- | --------------------------- | --------------------------------------------------------- |
| 탭 바·화면 전환 스택                      | 네이티브(Expo Router)       | 제스처·전환 애니메이션·뒤로가기가 네이티브 표준           |
| 앱 시작 화면                              | 네이티브                    | 앱 진입점. 로그인/회원가입 버튼이 WebView 화면으로 라우팅 |
| 앱 잠금·간편비밀번호 입력                 | 네이티브 화면               | 생체인증·키패드 UX·보안 저장소 접근                       |
| 푸시 수신·딥링크 진입                     | 네이티브                    | OS API 필요                                               |
| 로그인·가입 폼, 상품·콘텐츠·마이페이지·폼 | WebView(=web과 동일 페이지) | 콘텐츠 밀도·배포 없는 수정·웹과 기능 공유                 |

즉 "앱 = 네이티브 껍데기 + 웹 내용물"이 아니라, **화면 카테고리별로 런타임을 명시 배정**하는 하이브리드.

### 4.2 WebView 체감 성능 — 선택지 검토와 결정

WebView 화면의 체감 느림 원인은 세 가지다: WebView 프로세스 초기화, HTML/JS 다운로드, 데이터 fetch. 각각에 대한 선택지를 비교해 결정한다.

| 원인             | 선택지                                                            | 결정                                                                                                                    |
| ---------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| WebView 초기화   | ①매번 생성 ②탭별 인스턴스 상주 ③앱 시작 시 미리 초기화            | **②+③**: 탭마다 WebView를 하나씩 유지하고 앱 부팅 시 base URL을 미리 로드. 탭 전환 시 이미 살아있는 인스턴스가 보임     |
| HTML/JS 다운로드 | ①매번 전체 로드 ②SSR로 첫 화면을 서버가 렌더 ③캐시 헤더+번들 분할 | **②+③**: 공개 페이지는 Next.js SSR이라 WebView가 JS 완료를 기다리지 않고 HTML만으로 첫 화면 표시. 정적 자산은 장기 캐시 |
| 데이터 표시 공백 | ①빈 화면 ②스켈레톤(웹 CSS) ③네이티브 스켈레톤 오버레이            | **②+③ 혼합**: 웹이 스켈레톤을 먼저 그리고, WebView 자체 로딩 중에는 네이티브 오버레이를 얹어 이중 공백 방지             |
| 탭 간 상태 손실  | 탭별 인스턴스 상주(②)로 해결                                      | 스크롤·폼 상태 유지                                                                                                     |

측정: cold start→첫 페인트, 탭 전환 지연, 상품 목록 표시 시간을 기법 on/off로 비교 기록한다.

### 4.3 타입드 브릿지 (`packages/bridge`)

```ts
type BridgeRequest =
  | { type: "auth.biometric" }
  | { type: "auth.pin.open" } // 네이티브 간편비밀번호 화면 호출
  | { type: "push.register" }
  | { type: "share"; payload: { url: string } }
  | { type: "external.open"; payload: { url: string } };
type BridgeResponse<T> = { ok: true; data: T } | { ok: false; error: { code: string } };
```

- 메시지 계약을 한 파일에서 웹·네이티브 양쪽이 공유
- 웹: `window.ReactNativeWebView.postMessage` 래퍼 + request id 응답 매칭
- 네이티브: 핸들러 레지스트리 + 세션/권한 검사, `version` 필드로 웹-앱 프로토콜 버전 협상

### 4.4 인증·세션

- 네이티브는 refresh 토큰을 SecureStore에 보관. 앱 재실행·생체인증 통과 시 세션 복원 후 WebView에 주입
- WebView에서의 로그인/로그아웃은 브릿지로 네이티브에 통지 → 네이티브 저장소와 쿠키를 동기 정리
- 금융 민감 액션(출금·투자 확인)은 웹 폼 안에서 '네' 입력 확인 + 서버 재검증으로 처리

### 4.5 알림·딥링크

- expo-notifications 토큰을 API에 등록. 신규 상품 오픈·모집 마감·상환 입금 알림
- 알림 탭 → 딥링크 → 해당 탭의 WebView를 목표 라우트로 이동

## 5. 디자인 시스템

- 커스텀 토큰 config: colors·spacing·typography·radii scale + semantic 매핑 → tokens.css 생성, Button/Field/Steps 컴포넌트 + Storybook
- `tokens.json` export → app이 읽어 네이티브 스타일 상수로 사용
- 컴포넌트 카탈로그(web `/design-system` + 앱 내 미리보기 화면)로 회귀 확인

## 7. 완료 기준

- 투자 주문→상환 수령까지 실제 API로 동작하는 데모 시나리오 1개 완주
- 앱 첫 화면·탭 전환 체감 성능의 적용 전후 측정 수치 문서화
- 스키마 diff CI가 실제로 불일치를 잡는 것 확인
- Playwright E2E: 가입→입금→투자→상환 핵심 경로

## 8. 기술 과제 (해결·문서화 대상)

- 네이티브/WebView 역할 분리표를 코드 구조로 강제하는 방법(라우팅 규칙·브릿지 버전)
- 탭별 WebView 인스턴스 상주의 메모리 비용 vs 체감 성능 트레이드오프 측정
- 브릿지 계약의 타입 안전성 — 양쪽 공유 타입·버전 협상·미지원 API 폴백
- 투자 주문 폼의 낙관적 업데이트와 서버 검증(409) 충돌 처리
- 디자인 토큰 웹↔네이티브 단일 소스
- 목록 필터(슬라이더·다중 조건)의 URL 상태 동기화와 SSR 호환
